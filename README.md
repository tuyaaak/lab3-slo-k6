Энэ лабораторид өөрийн локал API серверийг ашиглан performance, reliability, availability гэсэн чанарын шаардлагуудыг шалгасан.

Серверт дараах гурван endpoint байгаа:

| Endpoint | Ажиллагаа |

## 3. SLO тодорхойлох

| Сценарио | SLI | Босго | Хэмжих нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` p95 latency | p95 < 50 ms | 20 VU, 1 минут |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 минут |
| Availability | Амжилттай checks-ийн хувь | > 90% | 20 VU, 2 минут, серверийн 10 секундийн зогсолт |
| Report performance | `/report` p95 latency | p95 < 450 ms | 20 VU, 1 минут |

### Босго сонгосон үндэслэл

**Performance:** `/cart/add` нь нэмэлт сааталгүй локал endpoint учраас p95 хугацааг 50 ms-ээс бага байхаар сонгосон.

**Reliability:** `/pay` endpoint ойролцоогоор 5% санамсаргүй алдаа үүсгэдэг тул хэлбэлзлийг тооцож 8%-ийн босго сонгосон.

**Availability:** 2 минутын туршилтад амжилттай шалгалтын 90%-иас дээш хувийг хангах зорилт тавьсан.

**Report performance:** `/report` нь зориуд 200–400 ms сааталтай учраас p95 хугацааг 450 ms-ээс бага байхаар тогтоосон.

### Error budget

Availability SLO = 90%

Туршилтын цонх = 120 секунд.

Зөвшөөрөгдөх зогсолтын хугацаа:

120 × (1 − 0.90) = **12 секунд**

Иймээс цагийн хувьд 12 секундийн алдааны төсөвтэй.

`checks`-ийн хувь нь серверийн uptime-ийг шууд хэмждэггүй. Энэ лабораторид хүсэлтийн амжилтын хувийг availability-ийн ойролцоо хэмжүүр болгон ашигласан.

## 5. Mini Chaos туршилт

Туршилтыг 20 виртуал хэрэглэгчтэй, 2 минутын хугацаанд ажиллуулсан. Туршилтын явцад серверийг ойролцоогоор 10 секунд зогсоож, дахин асаасан.

| Хэмжүүр | Бодит үр дүн |
|---|---|
| Нийт HTTP хүсэлт | 5763 |
| Амжилттай checks | 4798 |
| Амжилтгүй checks | 965 |
| Availability | 83.25% |
| HTTP error rate | 16.74% |
| Pay error rate | 19.78% |
| Availability threshold | FAIL |
| Reliability threshold | FAIL |
| Exit code | 99 |

### Availability тооцоо

Availability = (4798 / 5763) × 100 = **83.25%**

Тавьсан availability SLO нь 90% байсан боловч бодит үр дүн 83.25% гарсан.

Иймээс availability threshold хангагдаагүй.

### Error budget

2 минут = 120 секунд.

Цагийн error budget:

120 × 10% = **12 секунд**

Хүсэлтийн error budget:

5763 × 10% = **576.3 хүсэлт**

Бодит амжилтгүй хүсэлт = 965.

Хэтэрсэн хэмжээ:

965 − 576.3 = **388.7 буюу ойролцоогоор 389 хүсэлт**

### Ажиглалт

Серверийг зогсооход HTTP хүсэлтүүд амжилтгүй болж, error rate нэмэгдсэн. Сервер дахин ассаны дараа хүсэлтүүд хэвийн хариу авч эхэлсэн гэж ажигласан боловч сэргэлтийн яг хэдэн секунд үргэлжилснийг тусад нь хэмжээгүй.

Цагийн 12 секундийн budget болон хүсэлтээр тооцсон budget ялгаатай байв. Сервер унтарсан үед connection refused алдаа хурдан ирдэг тул богино хугацаанд олон хүсэлт амжилтгүй болж болно.

Мөн `/pay` endpoint-ийн алдааны хувь 19.78% болсон нь reliability SLO-ийн 8%-ийн босгыг давсан. Ингэснээр нэг тасалдал availability болон reliability хоёр шаардлагыг зэрэг зөрчиж болохыг харуулсан.

Цаашид серверийн сүлжээний хүртээмжгүй байдлыг төлбөрийн бизнес логикийн алдаанаас тусад нь хэмжих нь зөв гэж үзсэн.

Нотолгоо: `results/chaos.txt`, `screenshots/chaos.png`

## 6. Зориуд FAIL туршилт

Энэ туршилтаар `/report` endpoint-ийн p95 босгыг 450 ms-ээс 100 ms болгон зориуд хатууруулж, k6 threshold зөрчигдөх үед хэрхэн ажиллахыг шалгасан.

Туршилтыг сервер хэвийн ажиллаж байх үед 20 виртуал хэрэглэгчтэйгээр 1 минутын хугацаанд гүйцэтгэсэн.

| Хэмжүүр | Бодит үр дүн |
|---|---|
| Virtual Users | 20 |
| Хугацаа | 1 минут |
| Нийт HTTP хүсэлт | 2799 |
| Report p95 | 390.33 ms |
| Report threshold | p95 < 100 ms |
| Cart p95 | 1.14 ms |
| Pay error rate | 5.35% |
| Нийт HTTP error rate | 1.78% |
| Throughput | 45.67 req/s |
| Threshold үр дүн | FAIL |
| Exit code | 99 |

### Туршилтын үр дүн

`/report` endpoint нь зориуд 200–400 ms сааталтай ажилладаг. Тиймээс p95 хугацааг 100 ms-ээс бага байх босготой харьцуулахад шаардлага хангагдсангүй.

Бодит p95 нь **390.33 ms** гарсан бөгөөд k6 дараах алдааг мэдээлсэн:

```text
thresholds on metrics 'http_req_duration{name:report}' have been crossed
FAIL exit=99
```

Энэ удаагийн FAIL нь сервер унтарснаас бус, `/report` endpoint-ийн хариуны хугацаа тогтоосон threshold-ийг давснаас үүссэн.

Харин `/cart/add` endpoint-ийн p95 нь 1.14 ms, `/pay` endpoint-ийн error rate 5.35% байсан тул эдгээр үзүүлэлтүүд анхны SLO босгоо хангасан.

Энэ туршилтаар k6 нь чанарын шаардлага зөрчигдсөн үед exit code 99 буцааж, автомат шалгалтад алдааг мэдэгдэх боломжтойг баталсан.

## 7. Дүгнэлт

Энэ лабораторид өөрийн локал API-д зориулж performance, reliability, availability гэсэн гурван чанарын сценарио боловсруулсан. Сценарио бүрийн өдөөлт, шаардлагатай хариу болон хэмжүүрийг тодорхойлж SLO болгон хувиргасан. Performance туршилтад `/cart/add` endpoint-ийн хариуны хугацаа тавьсан босгыг хангасан. Reliability туршилтад `/pay` endpoint-ийн санамсаргүй алдааны хувь 8%-ийн босгоос бага байв. Нэмэлтээр `/report` endpoint-ийн p95 хугацааг хэмжиж, тайлангийн хариуны хурдыг шалгасан. Chaos туршилтаар серверийг түр унтраахад нийт хүсэлтийн амжилтын хувь 83.25% болж буурсан. Энэ нь 90%-ийн availability SLO хангагдаагүйг харуулсан. Мөн серверийн тасалдал `/pay` endpoint-ийн reliability хэмжүүрт нөлөөлж байгааг ажигласан. Энэ ажлын хамгийн их анхаарал шаардсан хэсэг нь чанарын сценарионы хэмжүүрийг зөв сонгож, k6 threshold болон error budget-ийн үр дүнтэй уялдуулах байв. Цаашид серверийн uptime, хүсэлтийн амжилтын хувь, төлбөрийн бизнес логикийн алдааг тус тусад нь хэмжих шаардлагатай гэж дүгнэсэн.
