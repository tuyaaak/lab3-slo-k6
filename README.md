## 3. SLO тодорхойлох

| Сценарио | SLI | Босго | Хэмжих нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` p95 latency | p95 < 50 ms | 20 VU, 1 минут |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 минут |
| Availability | Амжилттай checks-ийн хувь | > 90% | 20 VU, 2 минут, 10 секундийн зогсолт |

### Босго сонгосон үндэслэл

**Performance:** `/cart/add` нь нэмэлт сааталгүй локал endpoint учраас p95 хариуны хугацааг 50 ms-ээс бага байхаар зорилт тавьсан. Энэ босгыг эхний хэмжилтээр шалгана.

**Reliability:** `/pay` endpoint-д ойролцоогоор 5% санамсаргүй алдаа үүсгэдэг тул хэлбэлзлийг тооцож 8%-ийн босго сонгосон.

**Availability:** Серверийн 10 секундийн зогсолтыг багтаасан 2 минутын туршилтад амжилттай шалгалтын 90%-иас дээш хувийг хангах зорилт тавьсан.

### Error budget

Availability SLO = 90%

Туршилтын цонх = 120 секунд

Зөвшөөрөгдөх зогсолтын хугацаа:

120 × (1 − 0.90) = **12 секунд**

Иймээс 2 минутын хугацаанд 12 секундийн зогсолтын төсөвтэй гэж тооцсон.

Chaos туршилтын дараа бодит амжилттай болон нийт хүсэлтийн тоогоор тусад нь availability тооцож, цагийн error budget-тай харьцуулна.

**Тайлбар:** `checks`-ийн хувь нь цагийн uptime биш. Энэ лабораторид availability-ийн хүсэлтэд суурилсан ойролцоо хэмжүүр болгон ашиглана.

## 5. Mini Chaos туршилт

Туршилтыг 20 виртуал хэрэглэгчтэй, 2 минутын хугацаанд ажиллуулсан. Туршилтын явцад серверийг ойролцоогоор 10 секунд зогсоож, дахин асаасан.

| Хэмжүүр | Бодит үр дүн |
|---|---|
| Нийт HTTP хүсэлт | 5763 |
| Амжилттай хүсэлт | 4798 |
| Амжилтгүй хүсэлт | 965 |
| Availability | 83.25% |
| HTTP error rate | 16.74% |
| Pay error rate | 19.78% |
| Availability threshold | FAIL |
| Reliability threshold | FAIL |
| Exit code | 99 |

### Availability тооцоо

Availability = (4798 / 5763) × 100 = **83.25%**

Тавьсан availability SLO нь 90% байсан боловч бодит үр дүн 83.25% гарсан. Иймээс availability threshold хангагдаагүй.

### Error budget

2 минутын хугацаа = 120 секунд.

Цагийн error budget = 120 × 10% = **12 секунд**.

Хүсэлтийн error budget = 5763 × 10% = **576.3 хүсэлт**.

Бодит амжилтгүй хүсэлт = 965.

Иймээс хүсэлтийн error budget ойролцоогоор **389 хүсэлтээр хэтэрсэн**.

### Ажиглалт

Серверийг зогсоосон үед хүсэлтүүд амжилтгүй болж, HTTP error rate өссөн. Сервер дахин ассаны дараа хэвийн хариу өгч эхэлсэн.

Цагийн 12 секундийн budget болон хүсэлтийн budget хоорондоо ялгаатай байна. Учир нь сервер унтарсан үед connection refused хариу хурдан ирж, богино хугацаанд олон хүсэлт алдаатай болох боломжтой.

Мөн `/pay` endpoint-ийн error rate 19.78% болж, reliability SLO-ийн 8%-ийн босгыг давсан. Энэ нь серверийн нэг тасалдал availability болон reliability гэсэн хоёр SLO-д зэрэг нөлөөлснийг харуулсан.

Availability нь бүх endpoint-ийн амжилтын хувийг хэмжсэн бол reliability нь зөвхөн `/pay` endpoint-ийн алдааны хувийг хэмжсэн. Цаашид серверийн хүртээмжгүй байдлын алдааг төлбөрийн бизнес логикийн алдаанаас тусад нь хэмжиж болно.
